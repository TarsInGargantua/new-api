# 每日余额重置

2026-09-15 角色规则：游客（0）和 test（2）权限一致，新建账号默认是游客，初始钱包额度为 0，也不领取注册或受邀奖励。普通用户（1）、管理员（10）、超级管理员（100）参与每日和手动余额重置，用户名 `admin` 不再例外。现有账号角色、历史消耗和请求次数不会被本次更新批量修改；管理员可在用户编辑页调整角色，修改角色本身保留已有余额。游客升级为普通用户后，下一次余额读取会按最近重置日期补足当天额度。

符合角色条件的未删除用户，每天北京时间 `00:00` 将钱包余额设为后台当前显示单位的 **100**。这是覆盖余额，不是每天增加 100；历史消耗、请求次数、令牌额度、订阅额度不随之清零。游客和 test 可以登录、管理自己的 API Key；额度为零时付费中转请求被拒绝，管理员手动给予额度后可正常扣费使用，余额不自动补充。

2026-09-14 的一次性余额归一化保留完成标记 `migration.balance_normalization_20260914_v1`，已执行过的站点不会重跑。尚未执行的环境只对当前符合角色条件的账号应用此步骤。

- USD 模式为 $100；CNY 模式为 ¥100；自定义货币按站内显示汇率折算；TOKENS 模式为 100 个额度单位。
- 新账号默认为游客、额度 0；显式创建为普通用户、管理员或超级管理员的账号获得当天额度。
- `users.balance_reset_at` 保存最近已重置的北京时间日期起点，由现有 GORM 自动迁移新增。SQLite、MySQL、PostgreSQL 使用相同逻辑。
- 每个服务实例启动时检查漏执行日期，此后在北京时间零点执行；余额读取及扣费也检查日期。数据库条件更新防止重启、多实例或定时任务重试重复补发当天余额。
- 经典版和默认版数据看板的余额操作为“重置”。用户必须输入与本人账号完全一致的用户名，调用已认证的 `POST /api/user/self/reset_balance`，请求体为 `{"username":"alice"}`。服务端只操作登录用户 ID，拒绝 admin 和错误用户名，沿用敏感操作频率限制。
- 手动重置可重复使用，不设每日一次限制。手动重置后，同一天的自动补偿不会再次重置；次日零点仍照常重置。
- 钱包余额以数据库为准，不再依赖 Redis 中的额度字段；钱包扣增额同步提交，不进入延迟批处理，避免旧扣费在重置后回写。用户资料缓存和其他计数的批处理继续使用。此变更增加钱包数据库读写量，部署时应关注连接池和延迟。
- 重置与扣增额通过数据库事务串行化。SQLite 手动重置在读取用户名前先取得写锁，避免并发请求导致 `SQLITE_BUSY_SNAPSHOT`。重置不取消在途调用，也不改变其历史用量。在途预扣费跨越重置时继续按原逻辑结算/退款，公司内部使用场景已接受由此产生的余额误差。

部署时应统一升级所有网关实例，避免旧版本继续通过余额缓存和异步批处理写入额度。前后端均需更新。没有为既有未记录的用量补造日志。

验证：`go test ./model ./service`，`go test ./controller -run '^TestResetOwnBalance'`；两套前端生产构建，默认版类型检查，以及本地模拟 API 的桌面/手机弹窗交互检查。

## 接受的行为与继续测试结果

用户已明确接受在途请求跨越重置造成的结算/退款误差，此项不再作为发布阻塞项，也不引入余额版本隔离机制。例如：余额 500000 额度时预扣 39，上游尚未返回时重置为 50000000；请求成功实际收费 14，最后余额为 50000025（$100.000050）；请求失败则退款为 50000039（$100.000078）。管理员直接覆盖余额沿用同样的结算顺序。测试以 `accepted balance drift` 命名，并验证后续调用正常。

继续测试与修复：

- 新增 100 段流式回复，在第 50 段暂停上游，分别执行手动重置、管理员清零、管理员覆盖余额。三个场景均完整返回全部内容与 `[DONE]`，没有遗漏或重复片段。清零时新请求被拒绝；恢复余额后原 Key 正常调用。
- 修复流式停止通道的发送/关闭竞态，工作协程在完成清理后才通知等待方；只在协程退出后读取最终接收计数。
- 修复日志共享计数与轮转标志的竞态，改用原子操作。
- 超时或客户端断开时先关闭上游响应体，解除阻塞读取，避免额外等待 5 秒。客户端断开专用竞态测试连续 10 轮通过。
- 更新后的 `go test -race ./router -run '^TestRyanBalanceResetRelay$' -count=10` 通过，覆盖 1000 次并发中转、200 次并发余额操作和 30 次在途余额变更流式测试（每条 100 段）。这些数字不包含其他串行用例，耗时不作为生产容量结论。

验证限制：

- 原有 `TestListModelsTokenLimitIncludesTieredBillingModel` 的数据库/用户上下文初始化问题已在未修改代码上复现；完整 controller 套件没有全部通过。余额重置专用 controller 测试通过。
